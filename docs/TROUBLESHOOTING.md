# Troubleshooting Guide

Common issues and solutions for local development, sync, and deployment.

## Local Development
- **Problem:** Dev server won’t start
  - **Solution:** Check `.env.local` for missing/invalid values. Run `npm install`.
- **Problem:** TypeScript errors after pulling main
  - **Solution:** Run `npm install` and `npm run build`. Check for breaking changes in `PROJECT_REFERENCE_SUMMARY.md`.

## Sync Issues
- **Problem:** Images not syncing to Airtable
  - **Solution:** Ensure Google Drive token is valid. Check logs from `scripts/sync_drive_images_to_airtable.ts`.
- **Problem:** Intake images not showing in gallery
  - **Solution:** By design, intake images only show in the intake snapshot section. See `PROJECT_REFERENCE_SUMMARY.md` for image display rules.
- **Problem:** Photos disappear after saving Testing or completing a workflow stage
  - **Solution:** Stage saves no longer reconstruct the shared image library from archival `Images` attachments, which can omit approved Drive photos. Non-image saves leave metadata untouched. Image edits are stage-scoped and merge with fresh saved metadata; conflicting edits require a reload rather than overwriting newer changes. This prevents future save-related loss but does not restore previously removed references. Recover those only from reviewed exact-SKU Drive sources; do not rerun sample-image backfill.
- **Problem:** Restored photos show in Listings but Photography still appears empty
  - **Solution:** Photography now loads its canonical metadata directly rather than reconciling it against old archival attachments. Valid metadata-only Drive photos stay visible, including excluded photos. Testing retains those same rows as Photography-stage context; it does not relabel them as Testing uploads.
- **Problem:** Unchecking one processed image excludes normally named Photography images
  - **Solution:** The listing selector now shares the gallery's eligible-image rules instead of managing only filenames containing `processed`. Unchecking one image keeps other eligible selections.
- **Problem:** Format checks hide or remove workflow photos
  - **Solution:** Automatic checks now inspect formats without deleting saved metadata or changing unsaved selections. Unsupported images stay visible with a warning: uncheck them before publishing, then replace/reprocess their source through Photography if needed. Unchecking preserves the source library. Temporary Drive access errors leave all photos and drafts intact; reopen the listing after access is restored to check again. Newly added sources remain unverified until saved and checked. The legacy `validate-workflow-image-metadata` action still performs cleanup and is not a read-only diagnostic. These changes do not restore previously lost references.
- **Problem:** Blue cards with sample text appear instead of product photos
  - **Solution:** The generic workflow image backfill can generate blue sample cards, including inverted lettering; these can be valid JPEGs, so format checks cannot distinguish them from genuine product photos. Inspect the source bytes and provenance, not color alone. The Bel Canto SKU 11750 audit confirmed three such archival sample JPEGs plus three files named `original--original.jpg` that actually contained HTML. Restore only reviewed real-photo references from the exact-SKU Drive folder, not these placeholders or HTML files. Do not rerun generic sample-image backfill.
- **Problem:** One SKU folder contains conflicting product labels
  - **Solution:** Folder names alone do not establish product identity. Hold ambiguous images until the actual item is confirmed; do not combine different variants into one listing. For example, the SKU 11787 audit found both `VARIABLE-CURRENT` and `AMP / HIGH-CURRENT` cable-label photos in its named export folder.
- **Problem:** Seller Hub shows no active listings after an eBay publish
  - **Solution:** Use **eBay Seller** to open the unfiltered `https://www.ebay.com/sh/lst/active` page and confirm you are signed into the seller account connected to the app. The app's Inventory API offer ID is not a Seller Hub listing filter. After a takedown and republish, use **eBay Listing** for the current listing ID; the previous listing URL remains ended. If a different app tab still has the old URL, refresh that tab.
- **Problem:** eBay publish fails with error 25007 and "Package weight is over the weight limit" for USPS Priority Mail International
  - **Check:** Compare the actual packed weight with all services in the selected fulfillment policy. The saved Proceed HPA 2 package is 100 lb; its old standard policy includes USPS international and describes a 69 lb limit. The garbled eBay error text containing 70 lb is not proof that the item itself weighs 70 lb.
  - **Fix:** Select a policy appropriate for the real weight and confirm its shipping charges before saving it. This seller's existing 70-150 lb policy uses calculated UPS Ground domestic and flat $600 international; it was approved for this item only. Do not reduce the recorded weight, edit the shared policy, or publish automatically to test the fix.
  - **Saved selection ignored:** Older server drafts omitted saved business-policy IDs and fell back to runtime defaults. Updated server drafts use the same policy field candidates as the frontend and retain default resolution only for missing/blank IDs. Deploy the server mapping fix before retrying from CloudFront. Saving a policy selection alone does not update or publish the existing eBay offer.
  - **Field-level feedback:** After a confirmed weight-limit rejection, review **eBay Business Policies > Fulfillment policy**. The selector is marked invalid and says to choose a compatible shipping policy while keeping actual packed weight unchanged. The same guidance appears in the publish error. Changing the selected policy hides the previous policy's rejection; it does not certify the new policy. Returning to the rejected policy shows it again; successful eBay publishing clears it. The feedback is scoped to the current listing/policy and resets on a full page reload.
  - **Limits:** This warning follows eBay's validation, not a guessed numeric cutoff from a policy name/description. The available policy data does not establish reliable service/destination weight limits for automatic preflight. Both frontend and backend changes require deployment before this feedback appears on CloudFront.
- **Problem:** Saving reports that `__ebay_body_template_copy_override__` is not writable
  - **Solution:** Create `eBay Template Copy` as a long-text field with rich text disabled. **Save Updates** saves the editor's HTML there, independently of the rendered listing body. Existing embedded copy is loaded as a fallback and moved into this field on the next save. Blank copy adds nothing to a template; without a template it stays saved and does not modify manually authored listing HTML. HEAA About Copy still uses the rendered body's `about` section. Do not add the internal `__...__` editor fields to Airtable.
- **Problem:** Listed At is blank after takedown and republish
  - **Solution:** Takedown clears the saved date and its in-page value. After successful publishing, the app reads the current Airtable record and restores a missing or invalid `Listed At`; updating an existing live listing preserves its saved date. A rejected `Listed At` write is reported explicitly rather than silently dropped. Repair an older affected record only from a known publish timestamp, not today's date or an assumed original publication time.
- **Problem:** Lifecycle Status shows only one channel when both listings are live
  - **Solution:** The Airtable workflow has single-channel status values. The lifecycle panel verifies the linked channels and displays both when Shopify is `ACTIVE` with an Online Store URL and eBay is `PUBLISHED`. A status-check failure is shown as a warning; saved IDs alone are not treated as proof that listings remain live.
- **Problem:** Shopify reports an active product but its storefront link is 404
  - **Solution:** GraphQL product creation/update and sales-channel publication are separate operations. Approval publishing now explicitly publishes the active product to Online Store and verifies its URL before reporting success. Publication failures are channel failures, not successful listing creation. An existing active product can be published through the authenticated local product-set API's `publish-online-store` action without recreating it or changing price, variants or images.
- **Problem:** Shopify Price appears saved but is blank after reloading the listing
  - **Cause:** Older field discovery did not recognize canonical `Shopify Price`. An initially blank record could therefore edit a synthetic legacy variant-price field; the configured-write fallback could discard that unknown field while saving other changes successfully. Queue projections also omitted canonical Shopify Price.
  - **Fix:** Updated discovery and queue reads recognize `Shopify Price`, infer its numeric type even when blank, and map known legacy aliases to the canonical field. Unknown Shopify sale-price writes now fail explicitly rather than being discarded. This code fix must be deployed before it affects CloudFront; it does not restore an unsaved amount automatically. Re-enter the intended price and use **Save Updates**, then reload to verify. Do not publish merely to save a draft price.
- **Problem:** Every eBay update uploads the approved images again
  - **Solution:** Image preparation now saves each source image's SHA-256 fingerprint and eBay URL in the existing `Workflow Image Metadata JSON`. The first update of an older listing still uploads its images once to establish trustworthy mappings. Later updates show **Checking eBay images** and reuse unchanged, accessible images; only additions, changed content, or missing/expired hosted images are uploaded. Reordering and excluding images change the gallery URL list without re-uploading unchanged files. Original source files are downloaded to verify their content, so image checking still takes some time.
  - **If verification or cache saving fails:** The publish action reports the error and does not publish an uncertain image list. Successful image preparations are saved before offer publishing, allowing retries to reuse them. No new Airtable field is required; do not manually edit `ebayHostedImageCache` values.
- **Problem:** Shopify has zero weight or incorrect dimensions despite a populated Shipping Dims field
  - **Solution:** Older Shopify mapping ignored a bundled weight and counted it as the first dimension. For `70lbs (27x25x12)`, current flat previews send native weight `70 POUNDS` and exclude `70` from the existing dimension fallback. Explicit weight and separate dimension fields still take precedence; malformed/conflicting weights must be corrected. This fixes outgoing previews, not existing live products automatically.
  - **Verify:** Use the authenticated product API's `?view=shipping` read to distinguish native measurement from custom dimension metafields and inspect the served API version. Default product reads remain unchanged; truncated variant results are not a complete audit.
  - **Native Packed product size:** This is a separate length/width/height control, not the package selector. The requested mapping is Packed product size + Weight + custom dimensions, with **Package when shipped alone** unchanged. The inspected API inventory/variant inputs expose no native packed dimensions, and current public measurement-input docs list only weight/package ID; automatic native-size sync remains blocked. Admin/CSV editing is documented, but requires a separately approved workflow and confirmed axis mapping. Do not claim that custom metafields or a package ID populate Packed product size; do not change defaults, add privileges, or republish just to test.
  - **Approved live repair:** Use the dedicated `update-shipping` action on the authenticated local product-set endpoint, not a full listing publish/update. It targets an existing variant's native weight and exactly three custom dimensions, with CAS protection and exact readback. Weight and dimension writes are separate; a failed request can be partial or unconfirmed, so re-read before retrying. Definitions/pins and native Packed product size remain separate work.

- **Problem:** Shipping dimension values exist through the API but are absent from Product metafields, including View all
  - **Check:** Inspect each shipping metafield's `definition` through the protected shipping read. `definition: null` confirms a saved unstructured value, not an existing editable/pinned definition. Category metafields and native Packed product size are separate controls.
  - **Fix after approval:** The app now generates `custom.shipping_width_inches`, `custom.shipping_depth_inches`, and `custom.shipping_height_inches`. Use matching PRODUCT definitions of type **Decimal number** (`number_decimal`); `dimensionDefinitions` verifies these even if product values are absent. Pinning controls main-page visibility. Old non-`_inches` values remain separate in `legacyDimensionMetafields`: creating new definitions does not copy them. Copy values only with product-specific approval through `update-shipping`, omitting `weightPounds` to leave native weight untouched. Do not delete old fields, change definition types, bulk migrate, or assume metafields fill the native L/W/H boxes.

## Marketplace Closure History

- **Problem:** A sale occurred but the app still shows the row as Listed.
  - **Current behavior:** The manual **Mark Sold - Ready to Ship** action sets the sold workflow status/date and locks publishing controls. The sale webhook handlers record events and attempt cross-channel closure but do not perform that workflow transition automatically. Live webhook registration/delivery must be checked separately.
  - **Scope:** Automatic sold transitions and a backend sold-state update lock are known gaps explicitly deferred by the user. Stock-sending behavior remains unchanged; do not treat the UI lock as a server-side guarantee or republish a sold item to correct its status.
- **Problem:** An active republished item still has `eBay Closed At` or a result saying the offer was withdrawn.
  - **Meaning:** These are read-only historical diagnostics, not current listing status or required listing inputs. **Marketplace Closure History** is hidden while the workflow item is listed or stale-listed on either channel. It reappears outside those listing stages, including when the record returns to Ready; open it to review retained results/dates in lifecycle-style summary cards. Use the live marketplace check for current status. The short history note sits above the cards with additional spacing; there is no separate history-help disclosure. Republishing hides the previous results without deleting them.
- **Problem:** A failed close attempt has a recorded close date.
  - **Meaning:** Older eBay code saved this date for failed attempts too. An error result does not confirm takedown. Future failures update `Close Result` without setting or clearing `Closed At`; successful withdrawal still records its date. Retained timestamps can predate the latest result. No historical dates are bulk cleared.
  - **API contract:** A failed takedown response still includes the attempt time in `closedAt`; always check `success`, not the timestamp alone.
